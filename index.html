01 · The method

Maker–checker, for agents.

In a bank, nobody should approve their own work. I hold agents to the same standard. This is the path a change takes by default.

  1. 01

    Specification

    I write what the change must do and how it will be judged.

  2. 02

    Maker

    A coding agent implements it, often in its own git worktree.

  3. 03

    Code checks

    Tests, validators and measurements decide everything that can be decided exactly.

  4. 04

    Checker

    An independent reviewer, usually a different model, checks the work and must end with an explicit verdict.

  5. 05

    Evidence

    What ran, what it found and why it passed stays with the change.

If a check fails or can't tell, the change goes back to the maker.

Code computes acceptance

Where a check can be exact (a test, a schema, a loudness meter, a frame-rate probe), code decides. Model judgment covers only what code can't settle.

The checker never made the change

Usually Claude implements and Codex reviews. On the game, Codex lanes also implemented, and both Claude reviewers and a separate Codex review checked their work. A verdict that is missing, quoted or hedged counts as a failure.

Failures become controls

Investigated failures are filed by what the check saw, why it happened and the reusable lesson, then turned into a test, a guard or a rule. Overriding a failed check takes an explicit human decision.
