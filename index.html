Maker–checker, applied to agents

In a bank, nobody approves their own work. I hold agents to the same standard. This is the path a change takes by default.

  1. SpecificationI write what the change must do and how it will be judged.
  2. MakerA coding agent implements it, often in its own git worktree.
  3. Code checksTests, validators and measurements decide everything that can be decided exactly.
  4. CheckerA different model reviews the work and must end with an explicit verdict.
  5. EvidenceWhat ran, what it found and why it passed is kept with the change.

By default, a change goes back if any check fails or can't tell. Overriding a failed check takes an explicit human decision.

Code computes acceptance

Where a check can be exact (a test, a schema, a loudness meter, a frame-rate probe), code decides. Model judgment covers only what code can't settle.

A second model reviews

The model that checks is never the one that made the change. Usually Claude implements and Codex reviews; on the game it was the other way round. A verdict that is missing, quoted or hedged counts as a failure.

Failures become controls

Investigated failures are filed by what the check saw, why it happened and the reusable lesson, then turned into a test, a guard or a rule. 121 records logged so far, 86 of them investigated and filed this way.
